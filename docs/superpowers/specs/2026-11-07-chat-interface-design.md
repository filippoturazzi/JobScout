# The conversational interface: Design Spec

**Date:** 2026-11-07
**Status:** Approved by the user on 2026-11-07.
**Supersedes:** the page layout in `2026-10-22-stage-5-sources-and-dashboard-design.md` §5.2
(a full-width input above a card list and a detail panel). That spec's other decisions stand:
polling every 2 s, cards reordering as scores arrive, English and pt-BR, the design system
shipped inside the package, no frontend build step.
**Background:** `docs/superpowers/notes/2026-11-06-chat-interface-idea.md`, the engine fixes in
commit `d96b367`.
**Screens:** `docs/superpowers/specs/assets/2026-11-07-chat-interface/` (exported from pen.dev,
1440x900, dark theme). They are the visual reference; this document is the behaviour.

## 1. Intent

JobScout has a working engine and no face. This is the face, and it is the last piece before
the user starts using JobScout daily and puts it in their portfolio.

The user wants it to feel like an AI chat: a clean screen with one text field, a paragraph
about the job, then a short conversation in which JobScout asks only what the paragraph left
out, with answers given by clicking options. Once it knows enough, it searches and shows the
ranked jobs. Each conversation is saved in a left-hand list, so one person can keep separate
searches: another role they want, or a search for a friend that they will show on screen or
send as a screenshot. The friend never opens the app.

Everyone runs their own copy on their own computer with their own LLM key. There is no hosted
version, no demo, and no account.

## 2. Goals, non-goals, anti-goals

**Goals**

- A stranger who clones the repo, sets an LLM key and runs `jobscout serve` can describe a job,
  answer a few clicks, and get ranked jobs, without reading any documentation beyond the setup.
- Several saved searches per person, each with its own answers and its own results.
- At most five questions, each asked only when the paragraph did not answer it (§5).
- Every screen in the assets folder exists and behaves as described here.

**Non-goals (later, not now)**

- Scheduling a search to run daily. The sidebar's clock icon in `02-home-with-searches.png`
  belongs to that later work; v1 shows no clock.
- Asking questions about a single job ("is this one remote-friendly?"). The composer refines a
  search; it does not chat about postings.
- Login, accounts, sharing a search by link.
- A light-theme mockup. The tokens already define it; the screens are dark only.

**Anti-goals (would make this a failure even if it worked)**

- Chat text generated by the LLM. The conversation is fixed questions and fixed sentences
  filled from extracted data: deterministic, translatable, and free. The LLM is called to read
  the paragraph and to score jobs, nothing else.
- Any secret in the interface. No field for an API key, ever. The interface only reports
  whether a key was found.
- A frontend build step or framework. Static HTML, CSS and plain JavaScript served by FastAPI.
- A screen that looks complete when it is not: an unfinished ranking says how many jobs are
  still waiting for a score; a failed source is named.

## 3. Constraints carried from the project

- Operator configuration (`.env`, `Settings`) is never edited from the interface. User
  preferences live in the database.
- LangGraph stays limited to the per-job matching graph. The conversation is plain Python in
  `pipeline`.
- Everything stays keyed by `user_id`; `api/deps.py::get_current_user()` remains the one seam
  for auth. A search adds a second key below the user, it does not replace it.
- TDD for all logic, no test touches the network or a real LLM.
- `jobscout-design/` moves into the package as `src/jobscout/web/design/` (stage 5 spec §4),
  and its tokens and components are the only source of colours, type and spacing.
- The server binds to `127.0.0.1` by default; nothing here changes that.

## 5. The conversation

### 5.1 Flow

1. The user writes a paragraph and presses "Start search" (or Enter). A new search is created
   and appears at the top of the sidebar, titled from the extracted role and level ("Junior AI
   Engineer"), or from the first words of the paragraph when there is no role.
2. One LLM call reads the paragraph (`matching.terms.extract_profile`). Besides what it extracts
   today, it returns `suggested_skills`: a handful of skills typical for the role, used only as
   options for question 5.
3. JobScout says what it understood ("Got it: AI Engineer, Python, LangChain, RAG, in Brazil.")
   and asks the questions that apply, one at a time, with a counter ("2 of 3").
4. After the last question, the summary. Each row's edit icon reopens that question. "Search
   jobs" saves the answers as the search's preferences and starts the run.
5. The run shows `05-search-running`, then the results replace it as they arrive.
6. Text typed in the composer after the summary or the results is a refinement: it is appended
   to the paragraph, the paragraph is read again, and the summary is shown again with the new
   values. Refining never starts a search by itself.
   - **A clicked answer always wins.** The new reading fills only what the user has not
     answered or edited, and never clears an answer.
   - If the new reading creates a need that was not there (it now mentions hybrid, so a city
     is needed), that question is asked before the summary comes back.

Extraction never writes preferences directly. What it reads is held by the conversation, and
only "Search jobs" turns the summary into the search's preferences. This changes today's
`pipeline.search._resolve_terms`, which writes `seniority`, `required_skills` and
`excluded_keywords` on any paragraph change: a run uses the confirmed preferences and does not
read the paragraph again.

Reopening a search from the sidebar shows the same conversation, the summary and its latest
results.

### 5.2 The questions

Asked in this order, each only when its condition holds. Single-choice questions answer on
click; multi-choice ones show "Continue" (the screen's one primary button).

| # | Question | Asked when | Options | Becomes |
|---|---|---|---|---|
| 1 | "What role are you looking for?" | Extraction found no search terms (today it raises `ValueError`) | None: typed in the composer, then read again | `search_terms` and the rest, from the extended paragraph |
| 2 | "Which level are you aiming for?" | `seniority` is empty | Intern, Junior, Mid-level, Senior, Don't mind (single) | `seniority`; for Intern and Junior, also `excluded_keywords` += senior, sr, lead, staff, principal |
| 3 | "How do you want to work? Pick all that fit." | `stated_work_modes` is empty | Remote, Hybrid, On-site, Don't mind (multi) | `work_modes`; Don't mind = empty |
| 4 | Location, see §5.3 | `stated_regions` is empty, or a city is needed | See §5.3 | `regions`, `excluded_regions`, city (§5.3) |
| 5 | "Which skills should count most?" | `required_skills` is empty | `suggested_skills` (multi) | `required_skills` |

What the paragraph states is not asked again, but it is not applied silently either: it
appears already filled in the summary, and only "Search jobs" turns it into filters. That is
the rule `matching.terms` documents: extraction may suggest a restriction, only the user's
confirmation applies one.

The "Got it" sentence and every question are fixed strings with placeholders, in both
locales.

### 5.3 Location

The question depends on the work mode answer.

- **Remote only:** "Where can you work from?" Options: the home country when known (from
  `stated_regions` or an earlier answer), "Anywhere", "Abroad, not <home country>" when the home
  country is known, "Other country" (typed). Abroad stores `regions=[]` and
  `excluded_regions=[home country]`.
- **Hybrid or on-site included:** first the country if unknown (same options minus Abroad),
  then "Where in <country>?" with "Anywhere in <country>" and "Other city" (typed). The mockup's
  São Paulo and Rio de Janeiro buttons are Brazil-only examples; the builder may offer common
  cities per country or only the two generic options.

**A city is stored together with its country.** Today a region that is only a city ("Recife")
makes Indeed skip the search, because Indeed needs a country, and gives LinkedIn a place it may
not resolve. Required behaviour once a city is chosen:

- Sources are searched in the country, and LinkedIn with "<city>, <country>".
- A non-remote job passes when its location names the city, or names the country but no city
  at all. A non-remote job in another city of the same country fails.
- A remote job is judged by the country, as today.

How the city is stored (a new preference field or a structured region) is the builder's call,
with the upgrade SQL in the README as for earlier columns.

## 6. Searches and the data behind them

- A **search** belongs to a user and has a title, the conversation (paragraph, refinements,
  answers in order), its preferences, and its own matches. Two searches over the same job keep
  two scores.
- The fields of `UserPreferences` become per search. `Match` is keyed by job and search, and a
  search `Run` records its search.
- The shared parts stay shared: the `Job` corpus, the job embeddings, the sources.
- **A search scores only the jobs its own runs fetched** (decided by the user, 2026-11-07).
  The corpus is shared so a posting is stored and embedded once, but a friend's "data analyst"
  search never spends LLM quota on postings fetched for "AI Engineer". This needs a record of
  which search fetched which job; "waiting for a score" counts only those jobs.
- The operator's scheduled `match` job, which today scores for every user, scores for every
  search.
- A user can delete a search, which deletes its conversation and matches. Renaming is not in
  v1.
- **Upgrading an existing install keeps its data:** the current preferences become the user's
  first search, and its matches move with them. An SQLite table cannot drop a unique
  constraint in place, so this needs a one-time upgrade step (a script or a CLI command), not
  only the README's `ALTER TABLE` lines. The builder chooses which.
- **Today's single-profile interfaces follow the searches.** `PUT/GET /preferences`,
  `POST /search` and `GET /matches` become per-search routes (§7). The CLI's `jobscout search`
  and `jobscout matches` take an optional search id and default to the most recently used
  search, so the documented commands keep working. The dormant e-mail digest stays per user:
  it merges matches across the user's searches, one entry per job at its best score.
- Only one search runs at a time per instance: the scraped sources rate-limit, and SQLite has
  one writer. Starting a search while another runs returns a clear refusal that the page shows
  ("Another search is running"); a second start of the same search returns its run in flight,
  as today.

## 7. API

Thin routers over `pipeline`, as everywhere else. The page needs at least:

- Searches: list, create from a paragraph, read (conversation, answers, summary), delete.
- Answer a question; edit an answer from the summary; add a refinement.
- Start the search's run; read its progress (today's `GET /search/{run_id}`, scoped to the
  search).
- The search's matches, ordered and filtered as `list_matches` does, plus how many are still
  waiting for a score; set a match's status (exists).
- Status for the page: whether the configured provider's key was found (a boolean, never the
  key), the provider and model names, and the source statuses (`GET /sources` exists).
- The user's locale (`User.locale` exists). It switches the interface and the language of new
  explanations; explanations already written stay as they are (stage 5 spec §2).

The theme is a per-browser convenience and lives in `localStorage`.

## 8. States and errors

- **No LLM key:** `08`. Creating a search is refused server-side too, not only disabled.
- **The extraction call fails** (rate limit, network): the conversation shows one line saying
  what happened and a "Try again" button; the paragraph is kept.
- **What counts as a result:** every scored match the default listing shows
  (`list_matches`), with no score floor. Matches the cosine prefilter rejected (`low`, no
  score) are not results. "Found N jobs" counts these; "M more are waiting for a score" is the
  run's `remaining`.
- **Nothing found:** `09` appears when a finished run leaves zero results and nothing waiting
  for a score. With zero results but jobs still waiting, the page offers ranking them instead.
  The suggestions are built from the current answers and each changes exactly one: include
  remote, include hybrid, widen to the whole country, any level. Only the ones that would
  change something are shown. A suggestion changes the answer and updates the summary above;
  it does not search. "Search again" does.
- **Search again vs rank the rest:** "Search again" fetches from the sources and scores.
  When only scoring is left ("M more are waiting"), the action is "Rank the rest", which
  scores the waiting jobs without fetching (today's `run_match`), so the scraped sources are
  not hit again for nothing.
- **A source failed or was skipped:** named under the results, from the run's errors (for
  example "LinkedIn did not answer (too many requests)", "Indeed: not searched in Spain").
- **The ranking is partial:** the results message says how many jobs wait for a score.

## 9. Testing

- The conversation is server-side logic and is tested with pytest like the rest: which
  questions are asked for a given extraction, how each answer maps to preferences, the
  location cases in §5.3, refinements, the upgrade step on a database shaped like today's.
- Fake LLMs as today; no network.
- The page itself has no JavaScript test framework (no build step). It is verified by running
  the app and comparing each screen with its PNG, in both themes and both locales.

## 10. Calls made without the user, open to veto

- **No LLM-written chat text** (§2). Cheaper, translatable, predictable.
- **Single-choice questions answer on click, multi-choice ones need "Continue".**
- **Level Intern or Junior also excludes senior titles**, because seniority alone only nudges
  the score.
- **`suggested_skills` comes from the same extraction call**, not a second one.
- **Refining never starts a search by itself;** the user presses "Search jobs" again.
- **One running search per instance**, refusing a second (§6).
- **Delete but no rename** in v1.
- **Theme in `localStorage`, language in `User.locale`.**
- **A clicked answer beats a later reading of the paragraph** (§5.1).
- **No score floor on results;** the cards' score is the ranking (§8).
- **Widening suggestions change the summary; "Search again" searches** (§8).
- **"Rank the rest" scores without fetching** (§8).
- **The CLI and API follow the most recent search by default; the digest merges per user**
  (§6).
- **The "Which job boards should I search?" question that pen.dev added was removed:** the
  sources are operator configuration, shown in the summary line.
